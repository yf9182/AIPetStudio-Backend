# AI Pet Studio Backend

Dedicated Cloudflare Worker for AI Pet Studio. The Worker owns anonymous sessions, private R2 input media, generation task records, points operations and Vidu provider calls. The iOS app reads the Material Hub catalog directly and sends a validated material snapshot when creating a task; the Worker has no Material Hub runtime dependency.

## Local smoke test

```sh
npm install
npm run typecheck
npx wrangler d1 migrations apply ai-pet-studio-db --local
npx wrangler dev --local --port 8787
```

The catalog is loaded directly by iOS from Material Hub. The Worker does not expose catalog proxy routes and does not accept a Material Hub secret.

## Deployment order

1. The production resources are `ai-pet-studio-db` and `ai-pet-studio-assets`.
2. Apply migrations remotely, including `0004_v1_contract.sql`, `0005_remove_legacy_artwork_features.sql`, `0006_material_snapshot.sql`, `0007_welcome_bonus_state.sql`, `0008_direct_result_urls.sql`, `0009_purchase_recovery.sql`, `0010_pet_translator.sql`, `0011_pet_sound_library.sql`, and `0012_stripe_purchases.sql`.
3. Set `JWT_SECRET`, `REVENUECAT_SECRET_KEY` (V2 virtual currency), `REVENUECAT_V1_SECRET_KEY` (V1 subscriber lookup), `REVENUECAT_WEBHOOK_SIGNING_SECRET`, `REVENUECAT_WEBHOOK_AUTH`, and `VIDU_API_KEY` as Worker secrets. `JWT_SECRET` must be at least 32 characters; there is no development fallback. `REVENUECAT_WEBHOOK_SIGNING_SECRET` is the HMAC secret generated by RevenueCat; `REVENUECAT_WEBHOOK_AUTH` is the optional exact Authorization header configured on the webhook.
4. For web purchases, also set `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`, and point a Stripe webhook endpoint at `POST /v1/webhooks/stripe` subscribed to `checkout.session.completed` and `invoice.paid`.
5. After Firebase access is available, set `APP_ATTEST_MODE=required`, `APP_CHECK_PROJECT_NUMBER`, and optionally `APP_CHECK_APP_ID`; the Worker verifies the Firebase App Check JWT against the rotating Firebase JWKS.
6. Deploy the Worker and verify `/healthz`, bootstrap, wallet, one image task and one video task. The 10-minute cron only removes unreferenced upload objects older than 24 hours; task progress is advanced by App polling.

Generation pricing is enforced by the Worker: image tasks cost 10 points and video tasks cost 50 points, regardless of the Material Hub price field. Provider configuration uses `VIDU_BASE_URL`, `VIDU_IMAGE_MODEL` (default `viduq2`) and `VIDU_VIDEO_MODEL` (default `viduq3-pro-fast`).

The current contract exposes task history for the authenticated anonymous account. Sharing, sharing rewards, task deletion and task cancellation are intentionally not supported.

`GET /v1/tasks` returns the newest tasks first. It accepts `limit` (default 30, maximum 50) and an opaque `cursor`, and returns `items`, `next_cursor` and a summary containing `total_count`, `image_count`, `video_count` and `template_count`. Each item includes a `thumbnail_url`: a successful task uses the direct Vidu result URL, while other states use the original private input image when available. `media_url` and successful artwork `media_url` are direct Vidu URLs and must be downloaded without a Worker JWT. The App refreshes `queued`/`processing` items through `GET /v1/tasks/{taskID}`; each request performs at most one Vidu status lookup.

Deploy the Worker and verify this list contract before releasing the App build that depends on it. Completed result bytes are not copied into R2; the App persists them in its local task media cache.

## Task material snapshot contract

The App reads and displays Material Hub data directly. `POST /v1/tasks` accepts the selected snapshot and stores it with the task. The Worker never calls Material Hub and never accepts a client prompt outside the snapshot.

```json
{
  "template_id": "material-id",
  "material_snapshot": {
    "material_id": "material-id",
    "title": "Birthday",
    "kind": "image",
    "prompt": "...",
    "image_count": 1,
    "source_updated_at": "2026-08-26T00:00:00Z"
  },
  "input_asset_ids": ["users/<user-id>/uploads/<uuid>.jpg"],
  "client_request_id": "<uuid>"
}
```

`template_id` 可空，为空时 `material_snapshot.material_id` 与 `title` 同步可空（供未来用户自定义任务使用，任务标题回退为「自定义任务」）；模板任务仍须传齐快照字段且 `material_id == template_id`。Worker 只接受 `image_count == 1`，校验快照字段类型与 prompt 长度，并按 kind 固定计费（图片 10、视频 50）。重试使用任务中不可变的快照。

## Pet Translator V1

The Worker exposes two authenticated multipart endpoints:

```text
POST /v1/pet-translator/pet-to-human
POST /v1/pet-translator/human-to-pet
```

Each request contains `audio`, `species` (`cat` or `dog`) and optional `language` (currently `zh-CN`), plus a UUID `X-Request-ID` header. Audio is inspected from its container/frame headers and is limited to 10 MiB and 15 seconds. Supported formats are WAV, MP3, ADTS AAC and M4A/MP4 audio. The original recording is never stored in R2.

Pet-to-human uses Gemini structured JSON output for a conservative emotional interpretation. Human-to-pet uses Gemini to transcribe and classify the recorded human message, then selects one reviewed recording from the versioned cat/dog sound library. It never calls a speech or sound generation provider. The selected recording is stored under a private, shared R2 library key and returned through a short-lived task-scoped signed URL. Translation POST requests wait synchronously for a final result (up to 60 seconds): a new successful task returns `201` with `data.state=succeeded`, and an idempotent replay of an already settled result returns `200`. Normal success never requires polling; `GET /v1/pet-translator/tasks/{task_id}` is retained for one-time result inspection, signed audio URL refresh and manual investigation, and the signed audio route supports HTTP Range requests for AVPlayer.

If the app loses connectivity, is killed or times out before receiving the POST response, it does not automatically recover by querying the task. Keep the original recording and reuse the same `X-Request-ID` for a user-initiated resubmission; do not create a second request ID for the same recording. `503 PET_TRANSLATOR_PENDING` with a `task_id` means the task or its refund is still being finalized, so do not create another task or charge the user.

Translator pricing is configured in `wrangler.jsonc`; set the provider secret and keep the following variables aligned before enabling an endpoint:

```env
GEMINI_API_KEY=<Worker secret>
PET_TRANSLATOR_PET_TO_HUMAN_CREDIT_COST=10
PET_TRANSLATOR_HUMAN_TO_PET_CREDIT_COST=10
PET_TRANSLATOR_AUDIO_LIBRARY_READY=true
PET_TRANSLATOR_SOUND_LIBRARY_VERSION=v1
PET_TRANSLATOR_SOUND_LIBRARY_MIN_APPROVED=80
```

The existing RevenueCat V2 secret and Gemini key are required for both directions. Human-to-pet additionally requires at least the configured number of `approved` records in `pet_translator_sounds`; the ready flag alone never enables an empty or incomplete library. The scheduled Worker removes expired task results and retries pending refunds. Shared library files are not removed during task expiry or account deletion. Do not put provider keys in the iOS app or commit real values to `.dev.vars`.

The checked-in bundle contains 80 CC0 candidate recordings in `assets/pet-translator/library/v1` (cat and dog, 10 product expression labels, 4 recordings per label). Candidates start as `pending` because a person must listen to each clip and reject background noise, human speech, music, duplicates, or a wrong species before enabling the library. The product labels are entertainment mappings, not scientific claims about animal emotion.

Run `npm run pet-sounds:validate` to verify the 80-record manifest, local MP3 files, durations, licenses and SHA-256 values. After review, change the relevant manifest rows to `approved`, import the bundle with `node scripts/import-pet-sounds.mjs --upload --remote`, and set the ready flag only when the D1 approved count reaches the configured minimum. The importer uses source URLs only for audit metadata and never fetches them from a Worker request.

Human-to-pet success data includes `sound_id`, `sound_emotion`, `sound_intensity`, `audio_duration_seconds`, `sound_library_version` and `audio_url` alongside the transcript, meaning, emotion, intensity and `is_valid` fields. If the recording has no intelligible speech, or the detected expression has no reviewed sound, no sound is selected and the debit is refunded through the existing durable refund flow.

Apply `migrations/0010_pet_translator.sql` and `migrations/0011_pet_sound_library.sql` after the existing migrations before deploying a Worker build that exposes these routes.

For the iOS request and playback flow, see [宠物翻译 App 接入文档](docs/pet-translator-app-integration.md).

## Web purchases (Stripe)

The RevenueCat webhook only accepts events whose `source` is `in_app_purchase`, so a purchase made in the browser can never be credited through it. Web purchases are settled by a separate Stripe webhook that writes to the same RevenueCat virtual currency and the same `credit_ledger`, so a web buyer and an App Store buyer end up with identical wallet state.

```text
POST /v1/webhooks/stripe
```

The endpoint is pre-authentication (like the RevenueCat webhook) and verifies the `stripe-signature` header with HMAC-SHA256 over `{t}.{payload}` using `STRIPE_WEBHOOK_SECRET`, rejecting anything outside Stripe's ±300 second replay window. Signature verification uses WebCrypto directly; the Worker still has no runtime dependencies.

Credits are read from the `metadata` the web client attached when it created the Checkout Session (`aipet_customer_id`, `credits`, `product_kind`) — never from anything the browser can edit afterwards.

| Stripe event | Action |
| --- | --- |
| `checkout.session.completed` with `mode=payment` | Grants `metadata.credits` for one-off credit packs. Reference: `stripe:session:{id}`. |
| `checkout.session.completed` with `mode=subscription` | Ignored — the first invoice grants instead, otherwise it would be credited twice. |
| `invoice.paid` | Grants `metadata.credits` for the subscription's first and every renewal invoice. Reference: `stripe:invoice:{id}`. |
| everything else | Recorded by Stripe only; the wallet is never debited automatically. Refunds are reconciled manually in this version. |

Every accepted event is recorded in `stripe_webhook_events` keyed by the Stripe event id, so redeliveries are no-ops. A grant that cannot be applied immediately — most often because the RevenueCat customer does not exist yet, since web buyers never run the RevenueCat SDK — stays `pending`. Before the first adjustment the Worker calls `POST /v2/projects/{project_id}/customers` to create that customer (`409` is treated as already existing), and the existing 10-minute cron retries any still-pending grant through `retryPendingStripeGrants`.
